# ESP32-P4 v3 本地中文语音

当前默认流程为：本地 MFCC/DTW 模型负责全局唤醒，腾讯云 API 负责语音转文字，联网 AI（MiMo）处理完整指令，官方 ESP-TTS 保持本地中文播报。开机默认监听唤醒，各页面无需单独开启。转写和 AI 需要网络与已有服务配置。

## 使用

唤醒词为「你好 openvela」。大球页由当前大球接话，其他页面显示黑色全局小球。原本地语音页改为「语音服务」，提供开始联网语音、结束输入和本地播报测试；不再执行页面内的固定离线灯光/窗帘/风扇命令映射。识别文本通过现有助手处理，卡片状态继续以工具回执为准。

每次新的麦克风请求都获得独立编号，取消旧采音及连接，并等待资源清理后接管。排队期间只保留最新请求。输入框、大球、小球和语音页只接受自己的结果、只停止自己的录音；过期结果不会进入新输入或重复发送 AI。真实本地唤醒即使发生在另一个页面的录音中，也会建立新的接话请求。

采音线程连续处理小 DMA 缓冲，网络线程从有界 PSRAM 队列读取，按 200ms／6400 字节单声道 PCM 包发送。连接期间保留起音，结束时排空尾音；队列溢出、未收到完整 final、文本过长或句子缺失均拒绝发送截短命令。音频驱动、DNS 和系统调用的取消仍需等待调用返回，不承诺瞬时切换。

CLI（供手动排查）：

```text
desktop speech status
desktop speech listen
desktop speech say 你好
desktop speech stop
```

`listen` 使用联网转写；`stop` 结束当前转写并停止本地语音。

这是本地训练的 MFCC/DTW 声学模板分类模型。保持 54 个正例、144 个负例模板以及 329504 字节模型体积，使用最近三个正/负模板距离比判断。模型只从 `/sdcard/speech/custom/nihao_openvela.gkw` 加载，固件固定模型 SHA-256，模型和认证头必须一起更新。

最终候选通过合成开发测试和完整 C 流式测试。固定对比中，4% 音量弱语音检出由 18/36 提高到 34/36，负例误触发由 1/232 降到 0/232；两个噪声场景各少检出 1 条，完整结果应连同这些回退一起评估。两段各 15 分钟的连续合成负样本回放未出现唤醒，不能换算为真人误唤醒率或保证唤醒距离。训练记录见 `models/nihao_openvela.training.json`，扩样记录见 `models/nihao_openvela.expansion.json`。早期候选也用于开发迭代，现有测试集不应称为未触碰的最终真人验收集。

全局待机监听在开机后启动，页面打开本身不阻止监听，包括语音页和本地语音页；停止当前录音后自动恢复待机。联网语音识别录音期间，唤醒检测复用同一份 PCM，不另外打开麦克风；模型缺失或检测失败不影响原有识别。手动聆听使用统一联网转写入口。播放音频时仍暂停麦克风监听，播放结束后恢复。请说“你好 openvela”，稍作停顿后说问题。弱语音起音门限采用自适应噪声估计；高置信匹配可在 320ms 停顿后触发，其余保留 640ms 完整判定。真实麦克风唤醒事件在大球页面直接使用当前大球接话，不显示小球；其他 LVGL 页面才在左下角召出黑色 mini 小球与气泡，仅在连续空闲 6 秒后收起；语音输入、识别、AI／工具执行、设备核对或播报期间保持显示，完成后重新计时。进入页面和触摸不会召唤浮层。浮层录音期间切入大球页，会隐藏浮层并将原录音交给大球继续，不重启 ASR。已有录音会话收到新的真实唤醒时，将旧录音取消后交给新接话请求。相机直接显示路径使用独立快照叠加，浮层不进入保存的照片或视频。全局识别结果交给已有助手会话，音频交接保留独占锁。真人远场与实际房间噪声仍需现场复测。

10 倍训练命令在原训练命令上增加 `--room-augmentation --training-multiplier 10`，验证与测试样本量保持不变。需要同时运行 `test_custom_wake.py`、`test_wake_scenarios.py --asan`、`test_wake_handoff.py` 和 `test_wake_mini.py`，再同步模型、训练记录和生成的认证头并重构固件。

### 第三版：连续背景与声学适应性

原始语料仍为上述 670 段合成音频，没有新增真人录音。`--room-augmentation` 在固定的 54 个正例、144 个负例模板中覆盖合成底噪、80ms 回声和简单扬声器响应；仍保留干净模板，模型保持 329504 字节，DTW 模板对比次数不变。相同声学处理应用于正负两类，模板只来自训练声线；新增六类验证场景参与门限校准。

修复持续底噪可能提前触发语句开始、随后无法结束的问题：初始 80ms 估计底噪，初始估计限定上界，避免第一帧已有说话时把人声作为底噪；后续空闲帧继续跟踪底噪。保留现有 160ms 预录缓冲，不增加固定的语句结束等待时间。这不是 AFE 降噪或回声消除。

### 连续播报的权重缓存

后续版本在一次语音会话内保留 `front.bin` 和 `dec.bin`，合计 6,218,120 字节（约 5.93 MiB）。首次仍完整读取、校验和初始化；同一资源路径的后续播报复用已校验的内存权重，G2P 资源与计算工作区仍逐次释放。更换资源路径、合成失败或取消、显式停止、退出语音对话、切换到本地识别均使缓存失效。控制台连续 `desktop speech say` 也会复用缓存，结束后执行 `desktop speech stop` 释放。部署 SD 新模型前应停止语音会话。

释放接口不会阻塞 UI：若推理仍在使用模型，只标记失效，工作线程在退出合成时释放；空闲缓存立即释放。新增 `tts prepare` 日志区分 G2P、权重准备和缓存命中，`tts stages` 区分时长预测、声学前端和声码器。实板对比及释放证据位于 `output/speech-tts-cache-20261016/`。缓存主要改善连续播报，首次播报仍需加载和推理。

同一固件、同一实板的“你好”对比：首次首 PCM 为 37.14 秒，连续播报为 29.70 秒，减少 7.44 秒（20.03%）；权重准备从 8.12 秒降至 0。取消后重播重新加载权重，首 PCM 为 38.10 秒。G2P 约 2.6 秒、时长预测 0.05–0.06 秒、声学前端约 1 秒、声码器约 25–26 秒。以上为单次序列的观测值，不是时延保证。取消请求约 1.73 秒被控制台确认为完成，取消和空闲停止后均已回收模型缓存，麦克风与相机复开通过。主机首次/缓存命中输出逐采样一致，且与上一版中文 PCM 的 SHA-256 一致。

### 浮点卷积循环加速（2026-10-17）

`glass_speech_conv.h` 在 256 采样分块内每轮展开 4 个独立输出采样，增加标量 FPU 的指令并行度。每个采样仍按原输入通道/卷积核顺序累加，不启用 fast-math、不量化，也未启用 PIE SIMD。两类模型都使用该卷积实现；取消检查的分块边界保持不变。

主机 560 组卷积边界/膨胀/累加测试逐位一致，完整中文合成 PCM 与上一版 SHA-256 一致。实板“你好”首次首 PCM 为 29.15 秒，缓存命中为 20.63 秒；前版对应为 37.14 / 29.70 秒，连续播报首音等待减少约 30.5%。声码器由 25.26 / 25.82 秒降至 17.83 / 17.40 秒。取消后重新加载的首 PCM 为 29.47 秒。这些是两版固件的单板观测对比，不是最坏时延保证。构建、PCM 校验和实板回归证据保存在 `output/speech-tts-accel-20261017/`。

### 双核卷积与声码器热点（2026-10-17）

当输出通道至少为 2 且估算乘加数量达到 200,000 时，将 Conv1d 输出通道分为两段，主线程与辅助线程分别在 CPU 0/1 计算。较小卷积、单通道输出和转置卷积继续串行。线程创建失败回退串行。辅助线程每层创建并在返回前 join，不保留后台线程；每个采样累加顺序保持不变。取消回调在两线程间串行查询，共享取消标志，并通过内层计算保护范围退出；join 和同步对象清理完成后才向外层传播取消，调用者随后释放工作区。主线程临时亲和性在并行层结束时恢复。

声码器利用上游已有 stage callback 记录 `pre`、`up0/1/2`、`stage0/1/2_mix`、`pre_tanh`、`audio_pre_filter` 和 `audio` 的阶段间墙钟耗时，不读取张量内容。计时结果在推理后打印，`decoder_ms` 不包含这些日志打印的耗时。首音观测仍包括日志开销。

“你好”实板首次/缓存命中首 PCM 为 25.76 / 18.28 秒，前一版为 29.15 / 20.63 秒；这轮连续播报改善约 11.4%，并非双核翻倍。声码器为 14.59 / 15.13 秒。首轮有效热点数据中后两层残差块分别为 4.73 / 5.24 秒，是后续优化重点。该对比是不同固件的单板观测，不能当作最坏时延保证。主机 560 组卷积及完整中文 PCM 仍与单线程参考一致；验证与早期失败日志均保存在 `output/speech-tts-dual-20261017/`。

训练和流式测试均通过后，将模型、训练记录和生成的 `glass_wake_model.h` 同步到 `app/espdl-quickapp/models/` 及桌面源码；更新头文件后必须重新构建固件。测试脚本把候选模型的认证头与 C 源码一同暂存编译，避免引号头文件搜索规则误用旧哈希。准备脚本将自定义模型与官方中文命令模型一起放入 SD 资源包。`tools/deploy_speech_models.py` 可在本地局域网通过物理串口部署经过哈希校验的资源，只向指定板卡提供固定文件，先写 SD 临时目录，完成后原子发布。默认拒绝已有目标；仅自定义唤醒模型可显式 `--replace-existing`，停止聆听后将原目录改名留作回滚，发布失败则恢复原目录。不会格式化或写内置数据分区。

命令模型初始化必须有 `/sdcard/speech/esp-sr/fst/commands_cn.txt` 和匹配的 `mn7_cn/vocab`。本项目的 bootstrap 文件固定为 `speech/commands_cn.txt` 的八行 `命令编号,拼音`；准备脚本会补齐，已有 SD 可用部署工具 `--command-grammar app/espdl-quickapp/speech/commands_cn.txt` 补装。运行时在进入厂商构造函数前逐字节核验 grammar，并对命令模型资源校验哈希；缺失、空文件或错误内容会返回错误，避免触发厂商空指针路径。

本地控制台：`desktop speech listen/stop/status`；`desktop speech probe` 使用 `/sdcard/speech/test/wake-positive.pcm` 和 `wake-negative.pcm` 做纯离线推理，不打开麦克风。任务由长期桌面线程发起，避免 NSH 命令退出时销毁推理线程。ESP32-P4 线程启动时启用 PIE 与硬件循环，使用既有 NuttX 扩展上下文保存；已将当前板上会陷入非法指令的厂商 SIMD memcpy 替换为语音私有的 libc 拷贝，保留其余锁定推理内核。语音专用 DMA 有效载荷为 1984 字节，保留 64 字节对齐与四个缓冲，降低与其他设备共用片内堆时的压力。

## 构建和 SD 资源

在项目根目录运行：

```sh
python3 tools/prepare_speech_runtime.py --cache /path/to/speech-upstream --output /path/to/speech-prepared
```

准备脚本按 `upstream.lock.json` 的提交、大小和 SHA-256 验证依赖，生成 C 运行时、紧凑中文字典及 SD 资源。使用现有 ESP32-P4 v3 完整构建命令，额外加入：

```text
--speech-runtime /path/to/speech-prepared
```

历史 14+2 MiB 部署方案（当前实板仍保留 12+4 MiB，不执行数据迁移）：以下段落描述旧部署包。所有构建均只从 `/sdcard/espdl/` 加载视觉模型，不再读 Flash 模型区。16 MiB Flash 的前 14 MiB（`0x000000–0xDFFFFF`）用于启动及固件，固件仍从 `0x2000` 开始；最后 2 MiB（`0xE00000–0xFFFFFF`）为 `/data` 内置存储。部署包包含分类和人脸检测所需的三份视觉模型文件，以及 `/sdcard/speech/` 下的语音资源。

快应用安装支持选择内置 `/data/qpk` 或 SD `/sdcard/qpk`。桌面合并扫描两个位置并显示来源；应用键值和录音数据使用所在卷的 `qpk/.data`，卸载只清理对应卷。AI 生成应用在预览后保存时弹出位置选择，手机网页安装页也提供选择。没有 SD 卡时不会自动改装到内置存储；系统设置和草稿仍保存在内置存储。

首次升级此布局前必须备份旧 `/data`。旧版数据起点为 `0xC00000`，不能将旧 SmartFS 原始镜像直接写入新的 2 MiB 分区。使用旧固件的配对网页导出文件，或运行 `tools/backup_storage_export.py --url http://设备IP:8080 --output 本机备份.zip`（交互输入屏幕配对码），再用 `--verify 本机备份.zip` 校验。工具只读取旧固件数据，不烧录、不格式化。升级后首次挂载失败时按板级提示手动初始化新分区，再按可用空间恢复设置和应用；容量较大的应用重新安装到 SD。备份包含用户配置，勿放入公开部署包。当前未操作实机或迁移真实数据。

## 端侧指令与设备绑定

ESP-TTS 的已校验语音权重保留到最后一次归还后 60 秒，随后由桌面已有循环每秒检查并释放；连续播报复用缓存，加载或正在合成时维护检查立即返回，不阻塞界面。释放后下一次播报需要从 SD 重新读取并校验模型，因此长时间空闲后的首次播报包含加载时间。此策略不改变后台唤醒、模型、音色或音量。

AI 语音页的“离线指令”和 AI 工作区的“端侧语音”进入同一原生页面。选择灯光、窗帘、风扇各一台，再点“开始离线聆听”。说“你好 openvela”，稍作停顿，再说“打开灯光”“关闭灯光”“打开窗帘”“关闭窗帘”“打开风扇”“关闭风扇”“返回桌面”或“停止聆听”。唤醒和这八条固定指令在本机识别，不调用云端 ASR 或聊天服务；设备状态与控制仍使用已配置的 Home Assistant，必须能够连接该服务。原来的自由对话入口保留。

绑定由用户明确选择，只在当前页面会话有效；退出后重新选择，Home Assistant 的 URL/token 配置变化也会清空。不会自动选择第一台设备或向整个区域发送指令。只接受可用的 light/fan 和标明 curtain/blind/shade/shutter 类型的 cover，排除车库门、门锁和类型不明的 cover。

每条识别事件按所属语音请求和事件编号处理一次，超过 2.5 秒的不再执行，忙碌时不排队。执行前重新读取目标状态，已经达到目标则不发送控制；仅发送一次绝对开/关操作，并重新读取状态确认。响应丢失也只读回状态，不重发物理操作。底层 HA 服务将配置版本检查与控制提交放在同一个锁内，拒绝旧绑定向新配置发送请求。退出页面停止本页拥有的语音任务并关闭本页 HA 客户端，其他会话保持独立。

“返回桌面”和“停止聆听”不需要设备绑定，并优先于同一轮刷新的设备状态响应。停止按钮也会取消本页尚未发送的控制，并停止接收后续识别事件；已经发送的控制无法撤回，页面会提示查看设备状态。重新点击“开始离线聆听”后恢复指令接收。此页面不自动打开麦克风；绑定期间需要先停止聆听。唤醒模型仍是现有第三版 MFCC/DTW 模板，未因接通设备控制而重新训练；真人唤醒、口音和远场识别仍需单独验收。设备控制主机测试使用模拟设备，不代表物理设备已经开关验收。

## 唤醒运行开销优化（2026-10-23）

保持认证模型 `639825a5…`、特征顺序、相对门限、0.95 绝对距离包络、端点、冷却与音频所有权策略。RMS 将 int16 平方和改为 uint64 精确累加，再执行原 double 除法和 float 平方根；P4 单精度 FPU 下不再逐采样调用软 double 转换／乘加。预录环形缓冲按原 320 样本块复用，使用整块写入与最多两段拷出。

模板匹配保留原计算顺序；每组第三近邻成为有界 DTW 的截止距离，行下界已不可能进入前三名时提前返回。公开 `glass_wake_dtw()` 仍计算完整距离。模型构造直接持有已认证的原始文件缓冲，移除第二份权重拷贝，减少初始化峰值；常驻内存包含额外的 32 字节文件头与一个所有权指针，不能将峰值收益描述为常驻内存下降。

`tools/test_wake_runtime_unit.py --output <output>` 在 ASan／UBSan 下对照独立旧算法，覆盖 RMS 全 int16 取值、随机块、有界／完整 DTW、198 模板 top3 平局和晚到最优。`tools/test_wake_runtime.py --reference <冻结旧源码> --corpus <认证语料> --model <模型> --output <output>` 对照每个 feed 的事件、评估次数、score 位，以及每次提取的 416 个特征、ratio 和正模板距离。三个分块模式与七类合成开发场景共 5628 组；宿主 C CPU 基准另用未插桩运行库，模型和音频预加载，报告中位数与 P95。

新增模型内存测试 `wake_model_memory_host.c` 验证每次分配失败与再次构造／销毁。继续运行 `test_wake_distance.py`、`test_speech_barge.py` 和 `test_wake_handoff.py`。模型与门限的等价基线是本轮开始时的当前源码，已包含之前尚未部署的绝对距离过滤；不能把本轮与旧设备固件的差异全部算作运行优化。宿主耗时和合成回放不代表真实 P4 整机 CPU、真人远场唤醒率或电视环境误触发率；最终需单独标注是否完成构建、烧录与物理验收。
