连接方式：有互联网出口的路由器 LAN/交换机 → RJ45 → P4 `eth0` → NAT44 →
C6 `ap0` 热点 → 手机。不是用 C6 Wi-Fi STA 作为共享出口；现有 Wi-Fi 配置、
本地网页配置和蓝牙路径继续保留，未更新 C6 固件。

| 部分 | 本次实现 |
|---|---|
| 有线地址 | 复用原 `glass_netboot.inc` 常驻线程；单一 DHCP 所有者、半租期续租、掉线/过期清理与重新获址 |
| 有线快照 | 由原线程发布本次链路和租约状态，新的共享维护线程只读快照，不另起 DHCP 客户端 |
| 转发 | 固定 `ap0` → `eth0`，返回流量走 `eth0` → `ap0`；不因同网段 Wi-Fi 同时在线而改走 `wlan0` |
| NAT | 固定 SDK 原生 NAT44，TCP/UDP/ICMP；full-cone 模式；不启用 IPv6 或广播转发 |
| 开关 | `--ethernet-share` 显式开启；未开启时明确关闭 forwarding/NAT，避免复用准备区留下旧配置 |
| 网关 | 热点 DHCP 下发当前 AP 自身地址，支持选中备用 AP 网段后的动态网关 |
| DNS | 下发有线 DHCP 返回的 DNS；无 DNS 时用有线网关；客户端 UDP/TCP DNS 都通过普通 NAT 转发 |
| DNS 更新 | DHCP 网关/DNS 字段为原子值，可更新选项而不清空租约表；120 秒租约缩短客户端重新取 DNS 的等待 |
| 网段 | 开启时避开 eth0/wlan0 已有网段；有线出口新租约与运行中热点冲突时，用原名称/密码重开到备用网段 |
| 掉线 | 停止 NAT 并清理旧外部 IP 的映射；本地热点仍保留，重新获租后恢复共享 |
| 资源 | 最多 2 个 AP 客户端；候选 8 NAT 表最多 2048 条，使用 flat 构建 PSRAM 用户堆，条目净大小 36 B，另有分配器开销；转发预分配 4 个，动态增加配置为 0 |
| 容量诊断 | `desktop sharing` 输出 NAT 当前占用、峰值、2048 上限、达到上限次数及分配失败次数；候选 8 哈希桶位数为 8（早期为 4，候选 6/7 为 6） |
| 过期 | TCP 映射空闲 300 秒、UDP 60 秒、ICMP 60 秒；30 秒周期回收 |
| 错误 | 没有有效租约/DNS、接口掉线、网段冲突或 NAT 已由其他所有者启用时，不报告共享成功 |
| SDK 修补 | EEXIST 与 outbound ENOENT 分支补回解锁；NAT 锁改为 owner-recursive，允许端口选择器合法重入；原版失败反例与修正版均有记录 |
| 界面 | 热点页显示共享状态；网页网络状态增加有线连接/租约/共享及错误字段，无密码/令牌新增回传 |
| 诊断 | `desktop sharing`；绑定 eth0 的 `desktop ethernet-dns` 与 `desktop ethernet-probe <IPv4> <port>`；所有等待有界 |

`outbound/inbound` 是进入转发路径的计数，不能仅凭计数宣称应用数据已经送达。
界面“共享已开启”说明本机转发条件成立，上游互联网及手机浏览须另行实测。

实现入口为 `nuttx/net/espclaw_share.c`、公共 `espclaw_share.h`、

## Wi-Fi 6 可行性核对（未实施协议切换）

2026-10-26 核对官方 [ESP-FAQ](https://docs.espressif.com/projects/esp-faq/zh_CN/latest/software-framework/wifi.html)：
ESP32-C6 SoftAP 默认 b/g/n；官方给出先设置 20 MHz 带宽，再配置 802.11ax 的方法。
目标是 2.4 GHz、20 MHz 的 Wi-Fi 6，不能据此承诺 5 GHz 或路由器级吞吐。
数据手册的 802.11ax 摘要仍写 non-AP；具体 SoftAP 能力以当前 SDK、配置回读和真实客户端协商结果验证，
不能把通用能力位或 API 返回成功当成手机正在用 ax 的证明。

当前 C6 应用 SHA `087112e8e08ada7f91ee109de1e0f81553466d22482787df7d3c41178439adaf` 的匹配构建配置含
`CONFIG_SOC_WIFI_HE_SUPPORT=y`。匹配 ELF 中存在 `req_wifi_set/get_protocol`、
`req_wifi_set/get_bandwidth` 和 `req_wifi_ap_get_sta_list`，以及 STA 协商 PHY 查询函数。
当前 P4 热点业务路径没有调用这些协议/带宽设置及回读，尚无本热点的实际 ax 协商证据。
因此有实现基础，优先在 P4 补接现有 Hosted RPC：先只读协议/带宽，再按 20 MHz 与 b/g/n/ax
混合协议配置、核对回读、检查客户端 HE 信息并测上网/关闭。若当前 C6 返回不支持，再决定兼容的 C6 更新；
本次调查没有改无线协议或刷 C6。

## 实板失败与修正

候选 2 的有线 DNS 和 TCP 探测已通过，AP/DHCP/NAT 也曾进入 active，但随后

候选 3 仍在手机测试后出现停止阻塞。进一步核查发现两线程锁顺序反转：
TCP 选端口持连接表锁再取 NAT 锁，而转发持 NAT 锁再取连接表锁。

这仍不能代替手机实测，不推断所有现场故障都由此造成。

### D0/D1 接口与状态设计

优先修改 P4，复用当前 Hosted 2.0.13 的协议，不改 protobuf 生成文件和 C6 镜像。
已核对固定 Hosted 源中的以下消息；实现时还要将其定义与当前编译使用的生成头、响应处理表逐项比对：

| RPC | 作用 | 校验与证据边界 |
|---|---|---|
| WifiGetProtocol / WifiSetProtocol | 指定 STA/AP 的协议位图 | 校验接口、响应类型、UID、返回码及位宽；使用匹配 SDK 常量，不能抄 ESP-AT 的位定义 |
| WifiGetBandwidth / WifiSetBandwidth | 指定接口的带宽 | 请求、回读都应为 HT20；返回错误/缺字段不能当默认成功 |
| WifiApGetStaList | AP 上已关联客户端的能力信息 | 同时限制实际 num、protobuf 数组长度和本产品 2 客户端上限；phy_11ax 是能力/模式标记，不能单独代替实际数据 PHY 证据 |
| WifiStaGetNegotiatedPhymode | 设备自身 STA 的实际协商模式 | 固定 proto 中请求 339、响应 595；仅证明设备到路由器的连接，不证明手机到设备热点 |

通过既有 RPC 串行事务与常驻接收所有者调用，UI/NSH 只提交请求及读取快照。
新增解析不能把 0 返回码缺失、截断、未知枚举、延迟旧 UID 或重复响应当成功；堆分配失败须及时释放响应。
协议/带宽修改只在网络恢复 worker 的串行生命周期中执行，不在持有 netdev/socket/NAT 锁时等待 RPC。

首次 D0 仅读取 STA/AP 当前协议和带宽，不根据默认文档推断现场配置。
D1 在当前热点启动事务内扩展为：

1. 获取本轮 operation generation，校验无试连、停止或其它配置事务，保存原 STA/AP 协议与带宽。
2. 沿用 WifiStop → SetMode(APSTA) → SoftAP 配置与回读。
3. 设置 AP HT20，再设置 b/g/n/ax 位图；分别回读，只有匹配后继续注册/启动 AP。
4. WifiStart 后再次回读 AP 协议/带宽，验证 AP/DHCP/NAT ready；STA 重新关联/获址单独报告。
5. 启动失败、取消或响应超时只进入一次有界清理；超时可能已执行，先查询，不盲目重发设置。
6. 恢复保存的协议/带宽与原 STA 模式并回读。恢复顺序依兼容性调整：从 ax 恢复 HT40 时先关闭 ax，
   启用 ax 时先切 HT20。无法证明恢复完成则保持 state_unknown，禁止向 UI 发布 ready。

AP+STA 共用射频信道。D1 不静默修改用户 STA 协议/路由器配置；若 STA 当前 HT40 与 AP HE20 冲突，
明确报告共存限制，并用独立场景验证允许的组合，不靠反复断开 STA 掩盖问题。
协议偏好初期只在 RAM 测试，重启回已知行为；验收后再设计持久化，遵守配置保存与实体 Flash 显示验收规则。

诊断快照拟包含 operation_generation、configured_protocol、configured_bw、configured_verified、
sta_negotiated_phy、associated_client_count、client_he_capable_count、实际 SDIO clock/width，
以及 query_error/restore_error。时间戳和代次必须一致，旧快照不能覆盖新一轮停止结果。
产品界面区分“支持 Wi-Fi 6”“已开启 Wi-Fi 6 兼容模式”和“本次连接已确认 Wi-Fi 6”。
手机实际 ax 验收应结合客户端连接详情或受控抓包的关联/数据 HE 证据；无法取得时保持“协商未验证”。

### D2/D3/D4 调度与链路设计

当前 `c6net_txavail()` 只原子置 pending，既有 daemon 处理 devif_poll；必须保留此锁隔离。
当前 daemon 每轮最多 16 次 `esp_hosted_poll()` 后 sleep 10 ms。一次 poll 可以分发多个 Hosted 帧，
接收暂存上限 64 KiB，不能将 16 次轮询等同于 16 个包或据此计算固定吞吐上限。

D2 的首个候选采用常驻任务拥有的通知对象唤醒 TX，通知合并但不丢失处理期间的新通知。
RX 中断接入需另行验证；未接入时保留有界定时探测。按处理字节与单轮耗时限制 RX 批次，
每轮必须给 AP/STA TX、RPC 响应和停止清理机会；空闲时休眠，忙时短让出，禁止无限忙轮询。
初始时间预算由 D0 的批量耗时分布确定，不能把任意“更小 sleep”当性能修复。
对 RX 64 KiB 批次，应在安全分发边界安排公平性；不得中途释放/覆盖尚被回调引用的缓冲。

D3 在 20 MHz 完成枚举、读取 C6 CCCR 高速能力、使能高速并回读后，才切 C6 slot 到 40 MHz。
只影响 C6 所在 slot，不能同时提高 SD 卡时钟。打印 requested_clock 和 actual_clock，禁止仍固定打印“20MHz”。
当前 160 MHz 源/整数分频不把 50 MHz 列为可交付配置；50 MHz 需要独立时钟源/分频设计与信号完整性验证。
高频错误回退须等待 DMA 停止、清理传输所有权及已损坏会话，再恢复已知时钟/接口状态；
不在传输中直接改时钟，不把网络请求静默重发到对端。回退失败保持可诊断错误，停止共享。

D4 先量化每次 512 B CMD53 与 memcpy 成本；若做多块 DMA，必须保持 C6 FIFO 窗口地址、
完整块/末尾字节模式、DMA 对齐/缓存维护、信用计数和缓冲生命周期。原始分块路径保留为对照。
两端分片、64 KiB 窗口、短尾块、连接中断、超时与晚完成均需测试；不增加无界队列，不占用紧张内核堆放大元数据。

### Wi-Fi 6 第一阶段开发记录：候选 9

本轮实现 D0 的 PHY 可观测性及 D1 的 HE20 首选策略；D0 字节/等待时间统计、
D2 调度、D3 SDIO 40 MHz 与后续吞吐验收尚未完成。不能把协议功能与带宽提升混为一谈。

- 新增协议、带宽、AP 客户端能力列表及 STA 协商 PHY 的固定版本 RPC。
  请求 ID 为 297/298/299/300/311/339，响应 ID 加 256；复用原 UID 和串行事务所有者。
  protobuf3 的成功返回值 0 可以在 wire 中省略；仍必须具有正确响应类型和 oneof。
- C6 当前 IDF 5.5 的协议 ax 位为 `0x40`，客户端能力 ax 位为 `1 << 4`，
  STA 协商 HE20 枚举为 **6**。这些数值含义不同；旧资料的 PHY=5 不适用于本机。
- 热点启动在停止 Wi-Fi、安装并核对 AP 参数后保存 AP/STA 协议与带宽；
  首选 AP BGN+AX (`0x47`) / HT20 (`1`)。只写 AP，不改 STA 协议或带宽。
  开启失败时有界恢复并核对原 AP 配置，恢复成功才允许降级启动；恢复失败不发布就绪。
  WifiStart 后再次读回 AP 和 STA 配置，核对原 STA 配置未被改动。
- `esp_wifi_set_protocol` / `esp_wifi_set_bandwidth` 属于可持久化的 Wi-Fi 设置，
  因此两个 setter 在现有 RPC 锁内分别执行 RAM 选择、单次设置和 FLASH 选择恢复。
  RAM 选择失败也要恢复选择器；恢复失败返回 `-EUCLEAN`，不能被 PHY 回读成功掩盖。
  失败状态由关闭路径显式恢复后才能清除。未新增 P4 Flash 配置项。
- 常驻 recovery worker 在热点 READY 且无 STA 配网试运行时每约 15 秒刷新缓存；
  CLI 只读缓存，不在 NSH/RX/UI 回调中发查询事务。关闭立即使 PHY 和客户端缓存失效。
  STA 查询前后检查关联代次，避免断连后的旧结果成为当前协商证据。
- `desktop wifi6` 显示缓存代次、策略、配置回读、能力计数及独立错误；
  `desktop wifi6 off/on` 仅在热点已关闭且状态已知时改变下一次启动的 RAM 策略。
  off 明确选择 BGN/HT20，便于同固件对照；它不是“保留上次 C6 参数”。
  `he_capable` 只证明客户端上报 HE 能力，`sta_he20` 只描述设备到上游路由器，
  二者都不能单独证明手机到本机热点的实际数据 PHY。
