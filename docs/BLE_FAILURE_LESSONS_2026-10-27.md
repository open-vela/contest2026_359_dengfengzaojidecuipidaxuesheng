## 保留与撤回

保留错误码分类、有界输入副本、相对增量合并、按键边沿顺序、所有者／代次隔离、取消不重放和释放截止时间。这些路径在冻结候选的宿主／原生 UI 回归中有证据；真实按键拖拽仍没有实板验收，不能扩大为整机通过。

当前源码取消了自动调用 `ble_gap_update_params()`：只用官方 `ble_gap_conn_find()` 读取实际连接描述符，并在连接更新事件中刷新参数；跨重连原因记录继续保留。这个保守选择是本项目的收敛策略，不是宣称官方参数更新 API 本身错误，也没有证明主动调参就是本次 520 的根因。

同步调整了对应宿主夹具的预期，但遵照用户指令没有执行它，也没有生成新固件。

## 后续采用的方法

1. **启动优先**：先静态核对 SDK 临界区、调度锁、上下文恢复及锁顺序。没有完整证明前，不改 trap、不清零运行时锁、不绕过内存或 BSS 检查。
2. **一次一个变量**：启动恢复、输入队列、连接参数优化分别交付；性能参数保持保守，避免把多个改变混在一次烧录里追原因。
3. **官方协议加清晰边界**：使用标准 GAP／SMP／GATT／HID，应用层只做队列、背压、取消和诊断；队列接受、栈提交和对端收到分别报告。
4. **证据先于结论**：第一份失败不可覆盖；脚本故障、协议失败、启动失败分开。有限成功轮次不能证明长期稳定，更不能把旧候选结果套到新源码。
5. **当前保持停止**：不继续自动检查、烧录、重启或要求用户参与；未来操作应遵循届时的新指令。

官方参考：[NimBLE 返回码](https://mynewt.apache.org/latest/network/ble_hs/ble_hs_return_codes.html)、[GAP 描述符与连接更新 API](https://mynewt.apache.org/latest/network/ble_hs/ble_gap.html)。

## 继续修改：启动临界区静态审查

用户确认沿用上述开发方法。本轮只继续源码审查和修改，测试、构建、烧录、复位与实板操作仍暂停。

核对了仓库 HAL `nuttx/src/platform/os.c`，以及准备树
`/home/flash/vela-p4/network-share-20261026/nuttx` 中的
`include/nuttx/spinlock.h`、`include/nuttx/sched.h`、
`sched/sched/sched_unlock.c`、`sched/irq/irq_csection.c` 和 SDK `intr_alloc.c`。

- HAL 的每核 IRQ 嵌套计数是 `uint8_t`。原实现没有在递增前检查上限，也没有在递减前检查非零；错误配对或过深嵌套可能令其回绕，破坏最外层 IRQ 状态恢复。尚无现场证据证明发生过这种错误。
- 本轮只增加调试断言：访问每核数组前检查 CPU 下标，进入时检查计数上限，退出时检查非零。CPU 编号读取移至进入断言前；现有调度锁、SDK 递归锁的获取和释放顺序保留。
- 准备树配置为 `CONFIG_DEBUG_FEATURES=y`，但 `CONFIG_DEBUG_ASSERTIONS` 关闭。这批 `DEBUGASSERT` 仅在启用相应调试断言的配置中起诊断作用；本轮没有修改配置，也没有生成诊断固件。
- NuttX `sched_unlock()` 在任务调度锁计数归零时会进入内核临界区。SDK 中断分配路径存在持有 SDK 锁时分配内存的代码，共享 ISR 也在该锁内调用回调。这些路径仍需逐一核对内存分配、回调与内核锁的完整调用关系；仅凭两核 PC/RA 和锁地址不能确认锁所有权或唯一死锁链。
